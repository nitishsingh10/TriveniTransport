1. Scope & relationship to the PRD

The PRD (v0.4) defines what the product does and why — personas, functional requirements, the pricing model's shape, and the business/compliance context. This document defines how it's built: the concrete system architecture, the algorithms behind Section 8's pricing engine and Section 11's booking lifecycle, the API surface every client (web, customer mobile, vendor mobile) talks to, and the repository layout. Anywhere this document and the PRD could drift, the PRD's product decisions win — this document exists to implement them, not to reopen them.

Section references like "PRD §8.2" point back to the PRD; references like "§5.2" without "PRD" point within this document.

2. System architecture

Three client types talk to one backend service over HTTPS (REST) and WSS (real-time). The backend is a single Express process in Phase 1 (with an optional split into API + worker processes — see §12), backed by PostgreSQL for durable state and Redis for transient state (locks, cache, job queues).

2.1 Why one backend service, not several

With one vendor, three vehicles, and a Phase 1 scope this small, splitting into microservices would add deployment and consistency overhead with no corresponding benefit — the double-booking risk (PRD §16) specifically needs strong consistency between the availability check and the booking write, which is far simpler inside one service/one database than across service boundaries. The modular folder structure (§3) keeps the option to extract a service later (e.g. a standalone matching engine in Phase 2) without requiring it now.

4. Data model

Expands PRD §10 into concrete types and constraints. PostgreSQL via Prisma; uuid primary keys throughout; money stored as numeric(10,2), never floats; all "versioned" tables use effective_from/effective_to (open-ended = current) rather than in-place edits, per the PRD's non-retroactive pricing guarantee.

Booking.pricing_snapshot is the mechanism that makes rate changes non-retroactive: at quote time, the exact ZoneRate/Item/PricingRule row versions used are copied into this column, so a later admin rate edit can never silently alter an existing booking's total — even a re-render of the same booking always recomputes identically.

4.4 Not modeled as Postgres tables (by design)

  • Checkout locks — Redis keys, TTL-based, never persisted relationally (§5.5). Durability isn't the goal; automatic expiry is.
  • Layer-1 instant-estimate reference table — a Redis-cached or materialized-view lookup, periodically rebuilt from real Layer-2 Booking outcomes (PRD §8 Display strategy), not a hand-maintained table.

5. Core algorithms

Written as numbered procedures, not code — implementation language/library choices are free as long as the behaviour and guarantees below hold.

5.1 Instant estimate (Layer 1)

Purpose: a sub-500ms price range from just property type + pickup/drop (PRD §5, §8 Display strategy).

  1. Resolve pickup and drop coordinates to a LocationZone each (pincode match, or point-in-polygon if boundaries are geojson).
  2. Look up the pre-computed reference row for (configuration_type × zone_pair) in the Layer-1 cache.
  3. If that exact zone-pair isn't covered yet, fall back to a distance-band-only reference row (coarser, still fast).
  4. Return {low, high, zone_pair} with a plain-language "estimate only" disclaimer.

This never touches PricingRule/Item directly — it's a fast reference lookup, rebuilt periodically (§8, job reconciliation-layer1-refresh) from real Layer-2 outcomes so it doesn't drift from what customers actually end up paying.

5.2 Itemized quote engine (Layer 2)

Purpose: the authoritative, line-itemized quote once the inventory checklist is submitted (PRD §8.1–8.4). This is the single function both the initial quote and every on-site revision (§5.7) call.

  1. Zone charge: look up the active ZoneRate for (pickup_zone, drop_zone) as of now; if no direct zone-pair row exists, fall back to the distance-band rate computed from the geocoded distance (§5.3). Apply any active zone surcharge.
  2. Goods subtotal: for each declared line item, resolve the Item record (or the generic CFT-based fallback rate for a free-text item), then line_total = base_handling_rate × quantity × packing_tier_multiplier. Sum all lines.
  3. Total CFT: Σ(item.default_cft × quantity), using any customer-declared override for free-text items.
  4. Labour charge: read the active labour_threshold and per_extra_laborer_rate PricingRules. extra_laborers = ceil(max(0, total_cft − baseline_threshold) / threshold_block_size); labour_charge = extra_laborers × per_extra_laborer_rate.
  5. Surcharges: evaluate each active surcharge rule against booking context — floor_number with lift_available=false, scheduled_date inside the configured monsoon window, parking-distance beyond threshold (parking distance is a vendor-confirmed on-site field, not customer-declared, so this specific surcharge is typically applied as a §5.7 revision rather than at initial quote time).
  6. Add-ons: sum any customer-selected add-on rules (carpenter, electrician, carton retention).
  7. Total: zone_charge + goods_subtotal + labour_charge + Σsurcharges + Σaddons.
  8. Snapshot: persist the exact ZoneRate/Item/PricingRule row IDs and values used into Booking.pricing_snapshot (§4.3) — this is what makes a later admin rate edit non-retroactive.
  9. Return the full itemized breakdown (one line per component) for the "locked itemized quote" UI, plus the vehicle-capacity check (§5.5 note below).

Vehicle-capacity edge case: if total_cft exceeds every available vehicle's capacity_cft, the engine adds a second-trip line item rather than silently under-quoting (PRD §8 Edge cases).

5.3 Zone / distance resolution

  1. Geocode the pickup and drop addresses via the Distance Matrix provider (§9); cache the geocode result per normalized address string to avoid repeat calls for common buildings/societies.
  2. Match each resolved lat/lng to a LocationZone.
  3. Return {pickup_zone_id, drop_zone_id, distance_km} to the caller (§5.1 or §5.2).
  4. If the geocoding provider errors or times out, do not guess — return a clear "can't calculate distance right now" error and let the client retry, rather than falling back to a possibly-wrong estimate.

5.4 Vehicle availability & double-booking prevention

Purpose: guarantee only one booking can ever hold a given vehicle + date/slot — the PRD's top-severity risk (§16).

  1. Customer's availability calendar reads a REST snapshot on load, then subscribes to the WebSocket room availability:{vehicleId}:{date} for live updates (§7).
  2. On "start checkout": backend attempts SETNX lock:vehicle:{vehicleId}:{date} = draftBookingId with a 10-minute TTL (PRD §5 AC).
  3. If the lock is acquired: broadcast slot_locked to the room, so every other customer viewing that vehicle/date sees it go unavailable in real time.
  4. If payment completes inside the TTL: inside a single DB transaction, create/confirm the Booking row and delete the Redis lock key; broadcast slot_confirmed.
  5. If the TTL expires unpaid: the Redis key auto-expires; a keyspace-notification listener broadcasts slot_released so the slot reopens without any polling.
  6. Vendor-entered phone/walk-in bookings (PRD §6) go through this same lock→confirm path server-side — there is no separate code path that could let a phone booking silently conflict with an app booking.

Failure mode: PostgreSQL is the durable source of truth for confirmed bookings; Redis only ever holds transient holds. A Redis outage can't lose a confirmed booking — it can only block new locks, in which case the system should fail closed (reject new checkouts with a retry message) rather than risk a double-book by skipping the lock.

5.5 Booking state machine

The PRD §11 state table is enforced as a strict finite state machine: every transition is checked against an explicit allowed-transitions map server-side; anything not on that map is rejected (HTTP 409), regardless of which client or role requested it. Every successful transition writes an entry to a lightweight status-history log (booking_id, from_state, to_state, actor, timestamp) so the full lifecycle of any booking is reconstructable for support/disputes.

5.6 On-site revision approval flow

  1. Vendor app's add-item screen reads the same live Item catalog the customer saw at booking time.
  2. Vendor selects item(s) + quantity → backend runs the goods-subtotal portion of §5.2 (steps 2–3) against these new lines only, using rates effective now — deliberately not the original booking's snapshot, since a revision is genuinely new scope being added today, not a re-quote of the original items.
  3. Booking.status → Revision Pending; a Revision row is created (status=pending); customer is notified instantly via push/WebSocket, with SMS/WhatsApp as a fallback channel (§8, §9).
  4. Work on the affected step pauses until the customer responds.
  5. Approve: Revision.status → approved, its BookingItem rows are marked is_revision=true, Booking.final_amount is recalculated as base_quote_amount + Σ(approved revisions), status returns to In Progress.
  6. Decline: Revision.status → declined, Booking.status → Disputed, surfaced in the Admin dispute queue for manual resolution (PRD §11 — not automated in Phase 1).

5.7 Vendor assignment (pluggable module)

Phase 1: assignVendor(booking) always returns the single configured vendor_id, and picks the smallest active Vehicle whose capacity_cft ≥ the booking's declared total CFT (falling back to the largest vehicle, or flagging a second trip, if none is big enough alone).

Phase 2: the same function signature — (bookingContext) → {vendorId, vehicleId} | NoMatch — gets a real implementation (nearby vendors by service_areas, load- and rating-weighted scoring). Because every caller only ever depends on that input/output contract, Phase 2 genuinely only touches this one module, per PRD §9.3.

5.8 Notification dispatch

  1. A domain event (booking confirmed, revision logged, status changed, payment captured, etc.) enqueues a job on the notifications BullMQ queue with {bookingId, recipientRole, template, preferredChannel}.
  2. Worker renders the template and calls the provider: WhatsApp first (primary channel for this market), SMS as automatic fallback on WhatsApp delivery failure, Expo push for users with the mobile app installed.
  3. Retry: exponential backoff, max 3 attempts, then the job moves to a dead-letter queue for manual review rather than retrying forever.
  4. Final status (sent/failed) is written to the Notification row for Admin visibility (PRD §7).

7. WebSocket event specification

Socket.io, mounted on the same Express HTTP server (PRD §9.2). JWT passed at handshake; room subscription is authorized server-side per role — customers may only subscribe to their own booking's room, vendors to their assigned jobs, admin to everything.

Direction Event Payload / purpose
Client → Server subscribe_availability {vehicleId, date} — join the availability room for that vehicle/date
Client → Server subscribe_booking {bookingId} — join updates for one booking
Server → Client slot_locked A checkout hold started on this vehicle/date (§5.4)
Server → Client slot_released A hold expired unpaid; slot is open again
Server → Client slot_confirmed Payment completed; slot is now a durable Booking
Server → Client booking_status_changed {bookingId, from, to} — any state-machine transition (§5.5)
Server → Client revision_logged New on-site revision awaiting customer approval (§5.6)
Server → Client revision_resolved Customer approved or declined a revision

8. Background job specification

Redis + BullMQ, framework-agnostic (PRD §9.2). One or more worker processes consume these queues — see §12 for whether that's the same process as the API server.

Queue Trigger Payload Retry policy
notifications Any domain event (§5.8) {bookingId, role, template, channel} 3 attempts, exponential backoff, then dead-letter
invoice-generation Booking → Completed {bookingId} 3 attempts; failure alerts Admin
payment-webhook-retry Webhook handler failure (5xx from our side) {rawPayload, signature} Backoff up to Razorpay's own retry window; idempotency key prevents double-processing
reconciliation-layer1-refresh Nightly cron — (batch job) Recomputes the Layer-1 estimate reference table from recent Layer-2 outcomes (§5.1); non-critical, alerts on repeated failure rather than retrying aggressively

Slot-lock expiry (§5.4) deliberately does not go through a polling job — Redis TTL + keyspace notifications handle it natively, which is simpler and has no missed-poll window.

10. Auth & security design

  • Login: phone + OTP, no passwords — matches the norm for this market and avoids password-reset support burden for a small operator.
  • Tokens: short-lived JWT access token (~15 min) + longer-lived refresh token, rotated on each use and stored hashed in Session (§4.1) so any refresh token can be individually revoked (e.g. "log out this device").
  • RBAC: every route declares its allowed role(s); a shared middleware checks the JWT's role claim before the handler runs — enforced at the API layer, not just hidden in the UI (PRD §12).
  • Rate limiting: OTP request/verify and the public quote endpoints are rate-limited per phone number/IP to prevent abuse (OTP spam, quote-scraping).
  • Webhook integrity: the Razorpay webhook route verifies the provider's signature header before processing anything, and is idempotent via the stored razorpay_payment_id — replays or duplicate deliveries never double-charge or double-confirm a booking.
  • Transport & storage: TLS everywhere; no card data ever stored locally (Razorpay tokenizes); customer PII encrypted at rest (PRD §12).

Redis Managed — Upstash or Redis Cloud Needs keyspace notifications enabled for §5.4's slot-release mechanism

Environments: separate staging and production for both the database and the backend service — no pricing-rule or code change reaches production untested (PRD §12). CI/CD (conceptual): typecheck/lint/test on every PR; deploy web on merge to main; deploy backend on merge to main after tests pass; mobile builds triggered on version tag.

13. Open technical decisions

  • Geocoding/Distance Matrix provider — Google Maps Platform vs. Mapbox, decided on cost-at-projected-volume, not just feature fit
  • WhatsApp/SMS provider — MSG91 vs. Twilio, decided on India deliverability and per-message cost
  • Object storage for trust-page photos — S3 vs. Cloudinary, needed before Phase 1b, not Phase 1a
  • Whether the backend splits into separate API and worker deployables from day one, or starts combined (§12) — recommend starting combined and splitting only when justified by real load
  • Exact JWT access/refresh TTLs and OTP expiry window — security/UX trade-off, not yet fixed
  • Whether the Admin app is a separate Next.js route-group inside the same web app (as currently structured, §3) or a fully separate deployable — current recommendation is route-group, revisit only if admin and customer web start needing very different release cadences
